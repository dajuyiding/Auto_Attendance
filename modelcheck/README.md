# modelcheck：模型成色体检（含量化检测）

一套**可复现、可横向对比**的探针，用来回答三个问题：

1. 这个 API 背后的模型到底好不好？
2. 它是不是被量化过 / 被换成了小模型？
3. 我手上这几个供应商，差距到底有多大？

核心思路是：**单个模型自己看自己没意义，必须把同一批探针同时跑在多个端点上做横向对比。**
分数只有相对含义，但差异往往一眼可见。

---

## 一、先给结论：三层方法，按「简单 → 严谨」排

| 层 | 花多久 | 成本 | 能回答什么 | 需要什么 |
|---|---|---|---|---|
| **L0 鹈鹕测试（肉眼）** | 3 分钟 | 1 次请求 | 模型有没有「基本的结构理解」 | 什么都能做，最通用 |
| **L1 视觉探针（自动打分）** | 10 分钟 | 十几个请求 | 在上面基础上横向排序、可复现 | 任意 OpenAI 兼容端点 |
| **L2 确定性探针** | 15 分钟 | 十几个请求 | 能力差距有多大、哪些能力先崩 | 同上 |
| **L3 分布 / 协议指纹** | 5 分钟 | 几十个请求 | **是不是被量化了 / 是不是被换了模型** | 端点要支持 `logprobs` |

如果只想花 3 分钟：把下面这句话发给模型，然后自己看图。

```
Generate an SVG of a pelican riding a bicycle
```

## 二、鹈鹕测试：为什么它这么有效

这个测试由 [Simon Willison 在 2024-10 提出](https://simonwillison.net/2024/Oct/25/pelicans-on-a-bicycle/)，
后来形成了社区作品集 [pelicanbenchmark.com](https://pelicanbenchmark.com/)。

**为什么是「鹈鹕骑自行车」？** 因为：

- 这个组合在训练集里**几乎不存在**成品的 SVG，模型没法「背答案」，必须现场把结构推出来；
- 它同时要求：鸟坐在车架上、脚够到踏板、翅膀/前肢扶到车把——**多个物体的空间关系**；
- 输出是一段可执行的 SVG 代码，**错在哪里一目了然**：轮子不成对、鸟浮在空中、车架没连上，
  这些都不是审美问题，是**结构化推理的硬伤**。

**怎么判（人工，30 秒）**，按顺序看五项：

1. **两个轮子**：是不是两个尺寸相近的圆？半径够不够大？位置是不是在下方成对？
2. **车架**：两轮之间有没有连接结构（三脚架、前叉、座管）？
3. **鹈鹕的身体**：有没有一个块状的鸟身，落在哪个位置？是在车上，还是飘在车上面？
4. **喙**：鹈鹕最标志性的特征是巨大的喙 + 喉囊。画出来了吗？
5. **接触点**：腿有没有踩到踏板？翅膀有没有碰到车把？——**这一条最能区分模型档次。**

> 一个很实用的判据：**看它有没有「作弊」**。用 `<text>` 写「pelican on a bicycle」、
> 用一个黑色矩形当车架、把所有东西堆在同一点——这些都是退化输出的典型特征。

**局限**：它是「vibe check」，不是测量。同一个模型跑两次结果可能差很多；
社区作品集自己也声明不做排名、不验证模型名。所以它适合**发现问题**，不适合**下结论**。
要下结论就得用 L1/L2/L3。

## 三、怎么判断「是不是被量化过」——可测信号清单

先记住量化的量级（这样才知道自己在找多大的差异）：

| 量化等级 | 典型损失 | 参考 |
|---|---|---|
| 8-bit | 困惑度 +0.3%，几乎无感 | 主流评测 |
| 4-bit（AWQ / Q4_K_M） | 准确率 −1.8~2.1%，多数任务无感 | 主流评测 |
| 3-bit | 开始明显掉分 | — |
| 2-bit（标准 GPTQ） | **困惑度 6.14 → 38000+，MMLU 65.2% → 37.1%，基本不可用** | GPTQ / Ginger Labs |

KLD（KL 散度，衡量「用量化模型替代原模型的额外困惑」，参考
[smcleod 的 KLD 方法](https://smcleod.net/2026/04/measuring-model-quantisation-quality-with-kl-divergence/)）：

| Mean KLD | 含义 |
|---|---|
| < 1e-4 | 分布基本一致 |
| 1e-3 ~ 5e-3 | 非常接近，典型的好 6-bit |
| 1e-2 ~ 5e-2 | 可测的漂移，典型 4-bit 区间 |
| > 1e-1 | 显著发散，采样结果会明显不同 |

你没法在所有供应商上算 KLD（需要参考模型的完整分布），但可以**用它的精神做黑盒近似**：

### 3.1 分布糊度（需要 `logprobs`，最好用）

在**答案几乎唯一**的提示词上（`2 + 2 =`、`The capital of France is`、`7 times 8 equals` …）
只要 1 个 token 的输出，看首 token 的分布：

- **top-1 概率**：好模型在这种提示上接近 1.0；被量化后分布变平，**top-1 概率下降**；
- **熵**：同理，熵**上升**；
- **答对率**：更极端的量化会直接答错。这个指标最好用，因为它不依赖任何参考模型。


### 3.2 logit 浮点精度反推（本工具已实现，最有意思的一条）

出处：ICLR Blogposts 2026
[*Extracting Model Precision from 20 Logprobs*](https://iclr-blogposts.github.io/2026/blog/2026/precision-extraction/)。

原理很漂亮：`logprobs = logits − logsumexp(logits)`，也就是**所有 logits 被平移了一个常数 C**。
如果原始 logits 是低精度存储的，那么必然存在一个 C，使得
`(logprob_i + C)` 在低精度格式（FP8 / bf16 / fp16）里**精确落在格点上**。
于是枚举 C，看哪种格式能同时解释全部 20 个 logprob，取**尾数位最少**的那个。

论文实测结论（他们自己的方法）：

| 模型 | 反推精度 |
|---|---|
| gpt-3.5-turbo / gpt-4 / gpt-4-turbo | FP32 |
| gpt-4o / gpt-4o-mini / gpt-4.1 系列 | BF16 |
| gemini-2.0-flash / flash-lite | FP32 |

**重要**：反推出来是 BF16/FP16 **不是**「被量化」的证据——GPT-4o 本身就是 BF16。
只有明显粗于同批其他端点（尤其 FP8）才值得警惕。而且这个方法**只能看 logits 的精度**，
对 int4/int8 这类非标准格式会直接回落成 FP32，属于已知盲区。

### 3.3 tokenizer 指纹（抓「换模型」最硬）

固定几个字符串（英文、中文、代码、纯数字），看 `usage.prompt_tokens`。

> 同一个标称模型在不同供应商处，这几个数字**必须完全一致**。

对不上，就说明底层 tokenizer 不同 —— 那不是「同一个模型的量化版」，而是**另一个模型**。

### 3.4 漂移基线（抓「同一个端点悄悄变差」）

出处：arXiv:2512.03816
[*Log Probability Tracking of LLM APIs*](https://arxiv.org/abs/2512.03816)。

固定提示词、固定参数，只请求 **1 个 token**，把首 token 的 logprob 存成基线。
以后每次复测都跟基线比：**一次微调的改动量都能被测出来，而且比全量评测便宜 1000 倍。**

供应商说「我们换了个更快的推理后端」时，这是唯一能验证的说法。

### 3.5 最先崩的能力（不需要 logprobs 也能用）

量化/小模型在这些任务上**掉得最快**，因为它们是纯符号通路，几乎没有「语义兜底」：

- 多位数乘法（`4783 × 692`）
- 字母计数（`strawberry` 里有几个 r）
- 严格 JSON（不许套 markdown 围栏、字段类型要对、数组长度要对）
- 精确指令遵循（恰好 5 个词、全小写、末尾必须是 banana）
- 1..200 的完整列举（看截断、看循环）
- **长上下文召回**（needle in haystack）
- **中文长文**（很多被量化的模型中文先崩，会出现复读、编码坏掉）
- **修 bug 并真实执行测试**（最能区分「会写」和「像在写」）

## 四、怎么横向对比出差距

这是整套方法的关键，**不做这一步，上面的分数都没有意义**：

1. **固定变量**：同一个模型 ID、同样的 temperature、同样的 max_tokens、同样的提示词。
2. **同批跑**：把所有候选端点放在一次运行里跑同一套探针。
3. **加对照组**：
   - 一个**你确信没问题的基准**（官方直连）；
   - 一个**你确信被量化过的**（自己跑的 4-bit 本地模型）——用来标定量级；
   - 一个**简单任务**（画房子）——如果连这个都崩，说明模型已经严重受损，别的分数不用看了。
4. **存基线**：`--save-baseline` 存一份，之后 `--baseline` 复测，抓「悄悄变差」。
5. **看差距排序，不看绝对值**：`分数明显掉队 + 分布明显变糊 + 指纹对不上`，
   三条里中两条才值得下结论。

## 五、用法

```bash
# 1) 不需要任何 API key，先跑自检，确认工具本身没问题
python3 modelcheck.py --selftest

# 2) 看看有哪些探针
python3 modelcheck.py --list-probes

# 3) 复制模板，填上你的端点（api_key 支持 env:VAR 从环境变量读）
cp targets.example.json targets.json
python3 modelcheck.py --targets targets.json --out runs/2026-10-08 --jobs 4

# 4) 只跑视觉层（最便宜的体检）
python3 modelcheck.py --targets targets.json --only visual --out runs/visual

# 5) 存基线 / 复测漂移
python3 modelcheck.py --targets targets.json --out runs/today --save-baseline baseline.json
python3 modelcheck.py --targets targets.json --out runs/next  --baseline baseline.json
```

产出在 `--out` 目录里：

| 文件 | 内容 |
|---|---|
| `report.md` | 总览表 + 每个端点的探针明细 + 每条扣分理由 + 判定 |
| `report.json` | 原始数据，方便你自己再加工 |
| `gallery.html` | **同一个提示词下所有模型并排**，直接看图比高低 ← 最该看的 |
| `<端点>/pelican_svg.svg` | 原始输出，可以单独打开看 |

只依赖 Python 标准库（3.9+，用到了 `X | None` 和 `dict | dict` 语法）。

**建议的对比姿势**：把「官方直连」和「你怀疑的中转」放在同一个 `targets.json` 里，
`model` 字段写成一模一样的字符串——这样 tokenizer 指纹的交叉比对才会生效。

## 六、报告里每条判定是什么意思

| 信号 | 含义 | 怎么处理 |
|---|---|---|
| `visual_gap` / `capability_gap` | 分数比同批最好低一截 | 看 `gallery.html` 确认是不是真的差 |
| `logprob_disagree` | 高确定性提示答对率 < 85% | 分布已经不稳，重点怀疑 |
| `low_precision` | logit 精度反推明显偏粗 | 结合同批其他端点看，BF16/FP16 是常态，FP8 才需要警惕 |
| `tokenizer_mismatch` | 同 model 字段但指纹不同 | **底层不是同一个模型**，这条最硬 |
| `nondeterministic` | 温度 0 下三次结果不一致 | 网关缓存/路由，或采样参数被改写 |
| `precision_normal` | 反推为 BF16/FP16 | 信息性提示，不是问题 |

## 七、这些方法**做不到**什么（请务必读）

- **一次结果不能代表模型。** 采样有随机性，供应商后端也在变。同一个模型不同时间、
  不同温度、不同系统提示词，结果可能差很多。
- **自动视觉打分是启发式的。** 它靠几何规则判断「有没有画出两个轮子」「鸟是不是在车上」。
  它会误判（比如把眼睛当成头、把独轮车当成缺一个轮子）。**看图仍是最终裁判**，
  自动分只是帮你排序和抓明显缺件。
- **量化检测有盲区。** int4/int8 等非标准格式会让精度反推回落成 FP32；
  端点不支持 `logprobs` 时 3.1 / 3.2 / 3.4 全部失效（只剩 3.3 和 3.5）。
  而且**给 logprob 加随机噪声就能完全防住精度反推**——这是论文自己承认的，
  所以「没检测出来」不等于「没被量化」。
- **精度碰撞。** 更低精度的格点是更高精度格点的子集，所以粗格式能被细数据「假装」匹配。
  本工具取尾数位最少的匹配，并给出 `all_matching` 让你看到所有可能。
- **不能证明供应商身份。** 这套东西测的是「能力和一致性」，不是密码学意义上的认证。
- **它不替代正式评测。** MMLU / HumanEval / LiveBench 这类基准仍然是下结论的主力；
  这套探针的价值在于**便宜、直观、能定期跑**，适合做日常体检和排查。

## 八、自检覆盖了什么

`--selftest` 会跑完整条流水线（不需要任何 API key）：

1. **视觉打分器**在 Simon Willison 仓库的 8 个官方样例上排序是否合理
   （Claude 3.5 Sonnet 98.8 > GPT-4o 92.2 > Llama-3.1-8B 83.6 > GPT-3.5-turbo 53.1）；
2. **logit 精度反推**对 5 种合成格式是否 5/5 命中，且在随机 FP32 数据上 0 误报；
3. **每个确定性检查器**的正反用例；
4. **端到端**：起两个本地 mock 网关（一个正常 BF16、一个「被量化」成 FP8 且能力下降），
   跑完整套探针 + 报告 + 画廊，验证会话正确标出可疑的那个。
